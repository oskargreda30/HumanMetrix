# Multi-candidate Role Fit ranking

Candidates in the multi-candidate Role Fit comparison are **not** ranked by the
headline "Fit %" (overallFit) shown in the table. They are ranked server-side by a
**hiring band** (getHiringBandScore in server/routes.ts): must-have *critical*
skill gaps are weighted above overall fit, with fit % used only as a tie-breaker
within the same band. The server assigns `candidate.rank` and the
`candidateEntries` order; that is the single source of truth.

Consequence: a higher Fit % candidate can legitimately rank below a lower Fit %
one if the lower one clears more critical thresholds. Also note overallFit is
**capped at 74** whenever a candidate has any critical-skill gap, so any displayed
fit ≥ 75 implies zero critical gaps (and a report showing >74 alongside critical
gaps was generated by an older engine).

**Rule:** every surface that orders/ranks candidates must sort by `candidate.rank`
(rank asc; null ranks last; fall back to overallFit only when both ranks are null),
never by raw overallFit. This covers the PDF rankings table + heatmap
(client/src/lib/pdfExport.ts), the partner tab + admin tab bar charts, the partner
Skill Gap Heatmap, and the admin "Complete Candidate Ranking".

**Why:** a client flagged an 83% (Strong) candidate ranked below a 79% (Moderate)
one. Root cause was multiple surfaces re-sorting by raw overallFit while the
authoritative order is the hiring-band `rank`, plus PDF/guide copy that falsely
claimed "ranked by overall role fit score".

**How to apply:** when adding/editing any candidate list in the role-fit flow, sort
by `rank` and display `entry.rank` (do not recompute an ordinal client-side). Keep
user-facing copy describing the ranking as "hiring suitability — critical skills
weighted above overall fit".
